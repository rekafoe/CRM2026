# Mini App (Telegram MAP)

Публичная витрина: `GET /miniapp` — HTML-оболочка, которая подключает внешний bundle Mini App (см. `backend/src/utils/miniappIndexHtml.ts` и `frontend/src/miniapp/`).

## Сессия и заказы

- `POST /api/miniapp/auth` — `initData` от Telegram, ответ: подписанная HMAC-сессия `mapp1.*`.
- `GET /api/miniapp/me` — профиль.
- `POST /api/miniapp/orders/draft` — создаёт **черновик** заказа. Тело JSON: `{ customer, order: { items, order_notes?, design_help_requested? } }`.  
  `order.items[]`: `type` (как на сайте, часто id продукта), `params` (объект), `price`, `quantity`, `priceType` (например `standard`).  
  `design_help_requested: true` — клиент отметил, что макетов нет и нужна помощь с дизайном; в заметки заказа добавляется пояснение, файлы к позициям не обязательны.  
  Заголовок `Idempotency-Key` (8–128 символов: буквы, цифры, `. _ : -`) защищает от дубля после таймаута. Повтор с тем же телом возвращает `200`, исходный `order` и `itemIds`, с флагом `replayed: true`; повтор ключа с другим составом возвращает `409`.
  Первый ответ `201`: в теле `order` и `itemIds: number[]` — id строк `items` **в том же порядке**, что и `order.items` (для привязки макетов).
- `POST /api/miniapp/orders/:orderId/finalize` — финализирует черновик.
  Если `design_help_requested !== true`, backend проверяет, что для каждой позиции уже есть прикреплённый макет, и только потом выполняет финальное списание материалов. Повтор для уже финализированного заказа успешен и не повторяет списание.

## Параметры позиции для CRM

В `items.params` в Mini App рекомендуется передавать:

- `productName` — отображаемое имя;
- `description` — одна строка для списков;
- `parameterSummary` — `Array<{ label: string, value: string }>` (чипы в карточке позиции в CRM);
- `source: 'miniapp'`;
- для калькулятора: `calculator: true`, `configuration` — payload расчёта.

См. также [website-orders-integration.md](./website-orders-integration.md) (аналогия с заказом с сайта).

## Начальный экран и макеты

- По умолчанию открывается **каталог** (вкладка «Каталог» первая в нижней навигации).
- Загружаются все активные `active_for_site` товары. Верхний топбар переключает «Все», «Полиграфия», «Фотопечать», «Широкоформат», «Наклейки, стикеры» и «Сувениры».
- `MINIAPP_CATALOG_CATEGORY_ID` задаёт только стартовый фильтр, но больше не ограничивает загружаемый ассортимент.
- Карточки каталога повторяют `CatalogOrderCard` сайта: сетка 4/3/2/1 колонки, фото 4:3, заголовок слева, моноширинная цена и стрелка перехода; вся карточка ведёт к заказу.
- Визуал использует те же Inter/Manrope, тёплый фон, белые поверхности, рамки, радиусы и синие акценты, что и светлая тема сайта PrintCore; Telegram-тема не переопределяет фирменную палитру.
- Калькулятор повторяет структуру сайта: нумерованные шаги, моноширинные подписи полей, белые контролы и синие выбранные состояния.
- Price type представлен карточками со сроком, ценой каждого варианта, «Быстрее», «Выгода» и пояснением. Итог содержит чеклист выбранных параметров без разбивки по материалам и операциям.
- Файл макета выбирается в **калькуляторе до добавления позиции в корзину** и затем хранится в клиентском state до отправки.
- Если не отмечено «Нет макета — требуется помощь с разработкой», макет обязателен **для каждой позиции**.
- На экране оформления Mini App работает как пошаговый flow: **создание черновика -> загрузка макетов -> финализация**.
- При `design_help` сумма подписывается как **цена печати** + текст о расчёте дизайна по телефону, а финализация допускается без файлов.

## Черновик и финализация

Текущий контракт сделан атомарным:

1. клиент отправляет `POST /api/miniapp/orders/draft`;
2. получает `order.id` и `itemIds[]`;
3. загружает макеты к строкам заказа;
4. вызывает `POST /api/miniapp/orders/:orderId/finalize`.

Если загрузка файлов или финализация падает, заказ остаётся в состоянии `draft` и может быть дозавершён повторной отправкой из Mini App. Корзина очищается только после успешного `finalize`.

Draft-заказы не показываются в истории клиента (`GET /api/miniapp/orders`) и не открываются через detail до финализации.

Черновики старше 72 часов получают `miniapp_expired_at`: запись сохраняется для аудита, но загрузка файлов и финализация запрещены. Очистка не затрагивает финализированные заказы и другие источники. Настройки: `MINIAPP_DRAFT_RETENTION_HOURS`, `MINIAPP_DRAFT_CLEANUP_INTERVAL_MINUTES`, `MINIAPP_DRAFT_CLEANUP_ENABLED=false` для отключения.

## Загрузка макетов к черновику

После **успешного** `POST /api/miniapp/orders/draft` клиент сопоставляет выбранные в корзине файлы с позициями по **индексу** (`itemIds[i]` ↔ `i`-я строка корзины) и последовательно вызывает:

- `POST /api/miniapp/orders/:orderId/files` — `multipart/form-data`: поле `file`, при необходимости **`orderItemId`** (id из `itemIds` для этой позиции; не передавать = файл «на весь заказ»).

Ограничения: до 25 МБ на файл (и общие `UPLOAD_*` в окружении). `orderItemId` валидируется строго: файл можно привязать только к позиции этого заказа. После загрузки всех обязательных файлов клиент вызывает `finalize`.

После `finalize` догрузка запрещена и в UI, и в API (`409`). Позиции и уже прикреплённые макеты остаются доступными для просмотра и скачивания.

## План улучшений

Границы работ: публичная страница `/miniapp`, API `/api/miniapp/*`, Mini App checkout и `frontend/src/miniapp/`. Общий Telegram-бот, остальные сценарии CRM, сайт и n8n в этот план не входят.

### Этап 1. Надёжность контура

- [done] Автотесты проверки `initData`, сессии и сроков действия.
- [done] Идемпотентное создание черновика по `Idempotency-Key`: повтор запроса после таймаута возвращает исходный заказ и `itemIds`.
- [done] Повторная финализация возвращает успех для уже финализированного заказа и не списывает материалы повторно.
- [done] Черновики старше настраиваемого срока получают `miniapp_expired_at`; финализация и попадание в активную историю запрещены.
- [done] HTTP-прогон полного checkout на чистой базе: `201 → 200 replay → 409 conflict → 200 finalize → 200 replay`.
- [pending] Интеграционные тесты владельца заказа и загрузки/скачивания файлов.

### Этап 2. Клиентский сценарий

- Сохранение корзины и контактов между открытиями.
- Повтор предыдущего заказа.
- Самовывоз/доставка и оплата в одном checkout.
- Шкала статусов и встроенная поддержка.
- Устойчивая загрузка больших файлов и восстановление после потери сети.

### Этап 3. Постепенная модернизация frontend

Без единовременного переписывания: сначала вынести API и состояние из JS-строк в TypeScript-модули, затем перевести профиль и заказы на React, после этого корзину, checkout и калькулятор.

### Нефункциональные требования

- Повтор сетевого запроса не создаёт новый заказ и не повторяет списание материалов.
- Все операции с заказом и файлами проверяют владельца по Telegram `chat_id`.
- Цена и состав проверяются сервером; клиентский расчёт не является источником доверия.
- Финализированные заказы не изменяются задачей очистки черновиков.
